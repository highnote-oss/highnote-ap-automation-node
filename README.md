# Highnote AP Invoice Automation — Reference App

A reference application demonstrating end-to-end AP invoice automation on
[Highnote](https://highnote.com): per-invoice single-use virtual cards funded
on-demand, real-time collaborative authorization to enforce amount + MCC +
vendor matching, and webhook-driven reconciliation.

**Stack:** Fastify 5 + React 19 + SQLite (Drizzle ORM) +
[`@highnote-oss/nodejs-sdk`](https://github.com/highnote-oss/nodejs-sdk).

> **Reference implementation, not production-grade.** See [`SECURITY.md`](./SECURITY.md)
> for the deliberate gaps and a note on what "production" means in this codebase.

For other Highnote example scenarios, see the
[`highnote-examples`](https://github.com/highnote-oss/highnote-examples) catalog.

## What the demo shows

Three flows, end-to-end:

### 1. Invoice intake → single-use card issuance

The operator creates a `DRAFT` invoice (vendor, amount, expected MCC,
invoice number) and approves it. The backend:

1. Calls `cards.issueForApplicationWithOnDemandFunding` — a single SDK mutation
   that provisions both a per-card financial account **and** a virtual card
   funded on demand from the operator's master funding account.
2. Persists the returned `cardId` on the invoice row.
3. Transitions the invoice `DRAFT` → `CARD_ISSUED`.

The card exists only to pay this one invoice. It is closed (`cards.close`) as
soon as the cleared transaction reconciles.

### 2. Collaborative Authorization (CA)

Highnote sends an HMAC-signed CA request to `POST /collaborative-auth` for
every authorization attempt on a card issued through the AP product. The
demo's decision tree returns:

- `APPROVED` — the invoice exists, is unconsumed, and the requested amount
  and merchant MCC match the expected values.
- `INVALID_TRANSACTION` — no matching invoice for this card, or the invoice
  has been cancelled.
- `DUPLICATE_TRANSACTION` — the invoice was already consumed by a prior
  authorization (status `AUTHORIZED` / `CLEARED` / `RECONCILED`).
- `INSUFFICIENT_FUNDS` — requested amount exceeds the invoice amount.
- `INVALID_MERCHANT_CATEGORY_CODE` — the invoice declared an
  `expectedMcc` and the merchant's MCC doesn't match.

Highnote enforces a strict ~2-second response budget. The decision logic is
in-process, synchronous, and exercised by [`collaborativeAuth.test.ts`](./api/src/routes/collaborativeAuth.test.ts).

### 3. Webhook-driven reconciliation

The notification target subscribes to `CARD_PAYMENT_*` events. On receipt:

- `CARD_PAYMENT_AUTHORIZED_EVENT` → invoice `CARD_ISSUED` → `AUTHORIZED`.
- `CARD_PAYMENT_CLEARED_EVENT` → invoice `AUTHORIZED` → `CLEARED`, or
  `RECONCILED` if the cleared amount matches the invoice amount exactly. In
  either terminal state the backend calls `cards.close()` to revoke the
  single-use card.

All events are persisted to a local `webhook_events` table (deduped by event
ID) and rendered live in the operator UI.

## Required environment

| Variable | Required | Description |
|---|---|---|
| `HIGHNOTE_API_KEY` | Yes | Highnote test/live secret key (`sk_test_...` / `sk_live_...`). |
| `HIGHNOTE_CARD_PRODUCT_ID` | Yes | The AP invoice automation card product, ODF-enabled. |
| `HIGHNOTE_APPLICATION_ID` | Yes | A `Subscriber` or `BusinessAccountHolder` application. The backend derives the account holder ID from this at boot. |
| `JWT_SECRET` | Yes (in deployed mode) | Operator session signing secret. Auto-generated by Render via `render.yaml`; set explicitly on other hosts. In local dev a per-process random secret is used and tokens invalidate on restart. |
| `WEBHOOK_PUBLIC_URL` | No | Public URL where this server is reachable. Required to auto-register the webhook target and the CA endpoint when running outside Render. On Render, `RENDER_EXTERNAL_URL` is auto-detected. |
| `HIGHNOTE_ENVIRONMENT` | No | `test` (default) or `live`. Gates the `/api/simulate/*` routes off in `live`. |
| `PORT` | No | Defaults to `3000`. |
| `LOG_LEVEL` | No | Defaults to `info`. |
| `CORS_ORIGIN` | No | Defaults to `http://localhost:5173` in dev and same-origin only in production. |
| `CSP_REPORT_ONLY` | No | When `true`, the CSP is delivered as `report-only` for soak-testing changes. |
| `SQLITE_PATH` | No | SQLite file path. Defaults to `./data/app.db`. |

The full set with comments lives in [`.env.template`](./.env.template).

## Local development

### Prerequisites

- Node.js 22+
- A Highnote test API key
- A card product ID (AP invoice automation product, on-demand funding enabled)
- A subscriber or business account holder application ID

### Setup

```bash
git clone <repo>
cd highnote-ap-automation-node

# Where you put .env depends on which entry point you use:
#   • Local dev / `npm start`        → `api/.env`  (Node CWD is `api/`)
#   • `docker compose up`            → root `.env` (compose mounts it as env_file)
# The file format is identical; pick one or symlink the other.

cp .env.template api/.env
# Edit api/.env — fill in HIGHNOTE_API_KEY, HIGHNOTE_CARD_PRODUCT_ID,
# HIGHNOTE_APPLICATION_ID.

# Install + build both packages
npm run build

# Run dev (two terminals)
npm run dev:api   # Fastify on :3000 with `tsx watch`
npm run dev:web   # Vite on :5173 with /api proxy → :3000
```

Or run the production build single-process (Fastify serves the prebuilt SPA):

```bash
npm run build && npm start
```

Or via Docker (mirrors the Render deployment):

```bash
cp .env.template .env   # root .env for docker-compose
docker compose up --build
```

### End-to-end smoke test

With the API running locally (`npm start` or `npm run dev:api` in another
terminal) and a Highnote test environment configured, run:

```bash
npm run smoke
```

The script drives the full operator flow — signup, top-up, invoice creation,
approval, pay-by-link, simulate-authorize, and CA + webhook assertions — and
prints per-step pass/fail with elapsed timings. Override the target with
`SMOKE_BASE_URL` (defaults to `http://localhost:3000`). The first run requires
a funding account already registered on the Highnote dashboard for the
configured card product.

### Docker (local)

```bash
docker compose up --build
# App available at http://localhost:3000
```

## Deploy to Render

The repo ships with a [`render.yaml`](./render.yaml) Render blueprint.

1. Fork or import this repo into Render as a new Web Service from
   `render.yaml`.
2. In the Render dashboard, set:
   - `HIGHNOTE_API_KEY`
   - `HIGHNOTE_CARD_PRODUCT_ID`
   - `HIGHNOTE_APPLICATION_ID`
3. `JWT_SECRET` is auto-generated by the blueprint. `NODE_ENV=production` and
   `HIGHNOTE_ENVIRONMENT=test` are pre-set.
4. Create the service.

## Architecture

The demo runs as a single Fastify process serving both the API and the
prebuilt React SPA. SQLite stores users, invoices, webhook events, and
funding-account metadata; Highnote remains the source of truth for all card,
account, and transaction state.

```
                  +-------------------------------+
                  |  Operator UI (React SPA)       |
                  |  /  /pay/:slug  /docs          |
                  +---------------+---------------+
                                  |
                                  | /api/* (JWT)
                                  v
+------------------+   GraphQL   +-----------------------+
|  Highnote API     |<-----------+  Fastify (single proc) |
|                   |            |  - routes/             |
|                   |  HMAC POST |    auth, invoices,     |
|                   +----------->+    fundingAccounts,    |
|                   |  /collab.- |    collaborativeAuth,  |
|                   |   auth     |    webhooks, simulate, |
|                   |            |    payByLink,          |
|                   |  HMAC POST |    clientTokens        |
|                   +----------->+  - services/           |
|                                |    highnote,           |
+------------------+             |    webhookRegistration,|
                                 |    collabAuthRegistration
                                 |  - db/  (Drizzle/SQLite)|
                                 +-----------+-----------+
                                             |
                                       +-----+------+
                                       | SQLite     |
                                       | app.db     |
                                       +------------+
```

Two endpoints (`/collaborative-auth`, `/api/webhooks`) are public — Highnote
reaches them directly with HMAC-signed bodies and the raw payload is verified
before any handler logic runs. Everything else under `/api/*` is JWT-gated.

### Webhook + CA auto-registration

On boot, if a public URL is available (either `WEBHOOK_PUBLIC_URL` or
`RENDER_EXTERNAL_URL` on Render), the server:

1. Lists existing notification targets and CA endpoints, deactivates any prior
   `bay19-auto-*` entries left by previous deploys.
2. Registers a fresh notification target at `https://<host>/api/webhooks`
   subscribed to `CARD_PAYMENT_*` events.
3. Registers a fresh collaborative-authorization endpoint at
   `https://<host>/collaborative-auth`.
4. Holds the returned HMAC signing keys **in memory only** — never persisted,
   never logged, never exposed via the API. Both keys rotate on every deploy
   by design.

Endpoint names use a short SHA prefix (`bay19-auto-<short>`) so multiple
deploys don't collide on Highnote's side; the previous-deploy cleanup step
keeps the Highnote dashboard tidy. Failed registrations surface on the
**Webhooks** and **Collab Auth** pages with a **Re-register** button.

Without a public URL, both endpoints are still mounted but the server logs
"skipping auto-register" and Highnote never reaches them. The UI falls back
to polling.

## The ERP integration seam

In production, your AP system's `invoice.approved` webhook would call
`POST /api/invoices` with `{ vendorName, amount, invoiceNumber, expectedMcc,
... }`. The rest of the flow — single-use card issuance, CA enforcement,
reconciliation — is identical. The demo's web UI just exposes that same
endpoint as a manual entry form for live walkthroughs.

The CA decision tree itself is the other natural integration point: a real
deployment would call out to the vendor master, an approvals service, or a
3-way-match engine inside that handler instead of reading the expected values
straight off the invoice row.

## Status / not-for-production

- **Single-operator model.** Every authenticated user shares one
  `HIGHNOTE_APPLICATION_ID`. Production needs per-tenant scoping.
- **SQLite, ephemeral on Render.** Fine for the demo; swap for Postgres (or
  attach a persistent volume) for anything else.
- **No retry layer beyond Highnote's built-in webhook delivery retries.** No
  outbox, no dead-letter queue.
- **Single-region deploy.** The 2-second CA budget is generous but doesn't
  account for cross-region hops or upstream ERP latency.
- **`@highnote-oss/nodejs-sdk` is alpha** — pinned to `0.2.0-alpha.*` via a
  `file:` link during demo iteration.

See [`SECURITY.md`](./SECURITY.md) for the full list of deliberate gaps.
