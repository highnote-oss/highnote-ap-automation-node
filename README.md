# Highnote AP Invoice Automation — Reference App

A reference application demonstrating end-to-end AP invoice automation on
[Highnote](https://highnote.com): per-invoice single-use virtual cards funded
on-demand, real-time collaborative authorization to enforce amount + MCC +
vendor matching, and webhook-driven reconciliation.

**Stack:** Fastify 5 + React 19 + SQLite (Drizzle ORM) +
[`@highnote-oss/nodejs-sdk`](https://github.com/highnote-oss/nodejs-sdk).

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/highnote-oss/highnote-ap-automation-node)

> **Reference implementation, not production-grade.** See [`SECURITY.md`](./SECURITY.md)
> for the deliberate gaps and a note on what "production" means in this codebase.

For other Highnote example scenarios, see the
[`highnote-examples`](https://github.com/highnote-oss/highnote-examples) catalog.

## What the demo shows

Three flows, end-to-end:

### 1. Invoice intake → single-use card issuance

The operator creates a `DRAFT` invoice (vendor, amount, expected MCC,
invoice number) and approves it. The backend:

1. Calls `cards.issueForApplicationWithOnDemandFunding` — a single SDK mutation
   that provisions both a per-card Card Funding Account (CFA) **and** a virtual
   card funded on demand from the org's Product Funding Account (PFA).
2. Persists the returned `cardId` and `cardFinancialAccountId` on the invoice row.
3. Transitions the invoice `DRAFT` → `CARD_ISSUED`.

The card exists only to pay this one invoice. It is closed (`cards.close`) as
soon as the cleared transaction reconciles.

### 2. Collaborative Authorization (CA)

Highnote sends an HMAC-signed CA request to `POST /collaborative-auth` for
every authorization attempt on a card issued through the AP product. The
demo's decision tree returns:

- `INVALID_TRANSACTION` — no matching invoice for this card, or the invoice
  has been cancelled.
- `DUPLICATE_TRANSACTION` — the invoice was already consumed by a prior
  authorization (status `AUTHORIZED` / `CLEARED` / `RECONCILED`).
- `INSUFFICIENT_FUNDS` — requested amount exceeds the invoice amount.
- `INVALID_MERCHANT_CATEGORY_CODE` — the invoice declared an
  `expectedMcc` and the merchant's MCC doesn't match.
- `DECLINED` — the transaction is otherwise valid but the amount ends in an
  **odd** number of cents.
- `APPROVED` — the invoice exists, is unconsumed, the amount is within the
  invoice and matches any `expectedMcc`, and it ends in an **even** number of
  cents.

> **Demo decision rule:** once a transaction passes the validity checks above,
> the amount's trailing cent decides the outcome — **even cents approve, odd
> cents decline** (`$10.04` approves, `$10.05` declines). It's a deterministic
> switch for exercising both the approve and decline paths in the Test
> environment; flip the last cent to flip the decision.

Highnote enforces a strict ~2-second response budget. The decision logic is
in-process, synchronous, and exercised by [`collaborativeAuth.test.ts`](./api/src/routes/collaborativeAuth.test.ts).

### 3. Webhook-driven reconciliation

Highnote delivers a `NotificationEvent` nested under `data.node`; the receiver
reads `data.node.name` (the event type) and `data.node.node` (the detail), then
dispatches on:

- `PAYMENT_CARD_AUTHORIZATION_APPROVED` → invoice `CARD_ISSUED` → `AUTHORIZED`.
- `PAYMENT_CARD_AUTHORIZATION_AND_CLEAR_APPROVED` → single-step settle: invoice
  → `CLEARED` (or `RECONCILED` on an exact-amount match). This is the path the
  `/simulate` "pay invoice" (auth + clear) flow takes.
- `PAYMENT_CARD_CLEARED` → invoice `AUTHORIZED` → `CLEARED` / `RECONCILED`.

On any terminal settle the backend calls `cards.close()` to revoke the
single-use card.

All events are persisted to a local `webhook_events` table (deduped by event
ID) and rendered live in the operator UI.

## Deploy to Render

The repo ships with a [`render.yaml`](./render.yaml) Render blueprint
(single Docker web service + 1 GB persistent disk mounted at `/app/data` for
the SQLite file).

1. Click the **Deploy to Render** button above (or fork this repo and create
   a new Web Service from `render.yaml`).
2. Set the required environment variables:
   - `HIGHNOTE_API_KEY` — your Highnote API key (from
     [dashboard.highnote.com](https://dashboard.highnote.com))
   - `HIGHNOTE_CARD_PRODUCT_ID` — the AP invoice automation card product
     (on-demand funding enabled)
   - `HIGHNOTE_APPLICATION_ID` — a `Subscriber` or `BusinessAccountHolder`
     application (the backend derives the account holder ID from this at boot)
3. `JWT_SECRET` is auto-generated by the blueprint. `NODE_ENV=production` and
   `HIGHNOTE_ENVIRONMENT=test` are pre-set. `WEBHOOK_PUBLIC_URL` should stay
   blank — Render auto-injects `RENDER_EXTERNAL_URL` and the server picks it
   up at boot.
4. Click **Create Web Service**.

Once deployed, your app is available at `https://<your-app>.onrender.com`:

| Endpoint | Description |
|---|---|
| `/` | Operator UI (login, dashboard, invoices, funding, simulate) |
| `/pay/:slug` | Public pay-by-link page (no auth, hosts the Card Viewer SDK) |
| `/docs` | Swagger UI — interactive API documentation |
| `/health` | Liveness probe |
| `/api/webhooks` | Webhook receiver (public, signature-verified) |
| `/collaborative-auth` | CA receiver (public, signature-verified) |

### Webhooks + CA auto-registration

On Render, both the webhook target and the CA endpoint register themselves
automatically. Each deploy:

1. Detects the public URL via `RENDER_EXTERNAL_URL` (auto-injected by Render).
2. Removes any prior `bay19-auto-*` targets and endpoints so the Highnote
   dashboard stays clean.
3. Calls Highnote to register a fresh notification target at
   `<url>/api/webhooks` (subscribed to `CARD_PAYMENT_*` events) and a fresh
   collaborative-authorization endpoint at `<url>/collaborative-auth`.
4. Holds the returned HMAC signing keys **in process memory only** — never
   logged, never persisted, never exposed via the API. Both keys rotate every
   deploy by design.

Visit the **Webhooks** and **Collab Auth** pages in the app to see the live
registration status. If registration fails (transient Highnote outage,
expired key), use the **Re-register** button on each page to retry without
redeploying.

To use webhooks during local development, set `WEBHOOK_PUBLIC_URL` to a
public tunnel URL (e.g., from ngrok) and the same auto-registration flow
runs locally.

## Local development

### Prerequisites

- Node.js 22+
- A Highnote test API key
- A card product ID (AP invoice automation product, on-demand funding enabled)
- A subscriber or business account holder application ID

### Setup

```bash
git clone <repo>
cd highnote-ap-automation-node

# Where you put .env depends on which entry point you use:
#   • Local dev / `npm start`        → `api/.env`  (Node CWD is `api/`)
#   • `docker compose up`            → root `.env` (compose mounts it as env_file)
# The file format is identical; pick one or symlink the other.

cp .env.template api/.env
# Edit api/.env — fill in HIGHNOTE_API_KEY, HIGHNOTE_CARD_PRODUCT_ID,
# HIGHNOTE_APPLICATION_ID.

# Install + build both packages
npm run build

# Run dev (two terminals)
npm run dev:api   # Fastify on :3000 with `tsx watch`
npm run dev:web   # Vite on :5173 with /api proxy → :3000
```

Or run the production build single-process (Fastify serves the prebuilt SPA):

```bash
npm run build && npm start
```

### Docker (local)

```bash
cp .env.template .env   # root .env for docker-compose
docker compose up --build
# App available at http://localhost:3000
```

### End-to-end smoke test

With the API running locally (`npm start` or `npm run dev:api` in another
terminal) and a Highnote test environment configured, run:

```bash
npm run smoke
```

The script drives the full operator flow — signup, top-up, invoice creation,
approval, pay-by-link, simulate-authorize, and CA + webhook assertions — and
prints per-step pass/fail with elapsed timings. Override the target with
`SMOKE_BASE_URL` (defaults to `http://localhost:3000`). The first run requires
a funding account already registered on the Highnote dashboard for the
configured card product.

## Architecture

The demo runs as a single Fastify process serving both the API and the
prebuilt React SPA. SQLite stores users, invoices, CA decisions, and webhook
events; Highnote remains the source of truth for all card, account, and
transaction state. Behavior diverges in one place: **how webhooks and CA
endpoints are registered**.

### On Render (deployed)

```
Render Web Service (single container, /app/data on persistent disk)

  Fastify Server (port 3000)
  │
  ├── On boot
  │     ├── webhookRegistration.init()
  │     │     ├── reads RENDER_EXTERNAL_URL (auto-injected)
  │     │     ├── highnote.webhooks.list()      ─── removes prior bay19-auto-* targets
  │     │     └── highnote.webhooks.add()       ─── registers fresh target
  │     │           ├── subscribes to CARD_PAYMENT_* events
  │     │           └── signing key held in-process (never logged or persisted)
  │     │
  │     └── collabAuthRegistration.init()
  │           ├── reads RENDER_EXTERNAL_URL
  │           ├── highnote.collaborativeAuth.list()   ─── removes prior bay19-auto-* endpoints
  │           └── highnote.collaborativeAuth.addEndpoint()
  │                 └── signing key held in-process
  │
  ├── /                          → React SPA (Vite build, served static)
  ├── /pay/:slug                 → public pay-by-link page (no auth)
  ├── /docs                      → Swagger UI
  ├── /health                    → Liveness probe
  │
  ├── /collaborative-auth        → public, HMAC-verified, must respond <2s
  ├── /api/webhooks              → public, HMAC-verified, dedup on event_id
  │
  └── /api/* (JWT-protected)     → auth, invoices, fundingAccounts,
                                   simulate, payByLink, clientTokens, ...

  SQLite at /app/data/app.db (survives deploys via Render's persistent disk)
```

Key property of the deployed flow: signing keys live only in process memory
and rotate every deploy. There's nothing to copy or persist anywhere. Past
deploys' targets and endpoints are removed during boot so the Highnote
dashboard stays clean.

### Locally

```
Local dev (no public URL)

  Fastify Server (port 3000)
  │
  ├── On boot
  │     ├── webhookRegistration.init()
  │     │     ├── no WEBHOOK_PUBLIC_URL set, RENDER_EXTERNAL_URL not set
  │     │     └── logs "skipping auto-register" → server stays up, no signing key
  │     │
  │     └── collabAuthRegistration.init()
  │           └── logs "skipping auto-register" → same behavior
  │
  └── Receivers still mounted, but Highnote can't reach them
        └── operator UI drives card issuance, pay-by-link, and the
            simulate-authorize route via /api/simulate/authorize
            (which calls highnote.test.transactions.authorize directly --
             no inbound CA or webhook delivery happens locally)

  Vite dev server (port 5173) → proxies /api/* to :3000
```

Both receivers are still there if needed — set `WEBHOOK_PUBLIC_URL` to an
ngrok-style tunnel URL and the **same** auto-registration flow runs locally,
producing the same in-memory signing key behavior as production. Without
that env var, the demo runs entirely on operator-driven flows and Highnote
never reaches the local instance.

## The ERP integration seam

In production, your AP system's `invoice.approved` webhook would call
`POST /api/invoices` with `{ vendorName, amount, invoiceNumber, expectedMcc,
... }`. The rest of the flow — single-use card issuance, CA enforcement,
reconciliation — is identical. The demo's web UI just exposes that same
endpoint as a manual entry form for live walkthroughs.

The CA decision tree itself is the other natural integration point: a real
deployment would call out to the vendor master, an approvals service, or a
3-way-match engine inside that handler instead of reading the expected values
straight off the invoice row.

## Environment Variables

| Variable | Required | Description |
|---|---|---|
| `HIGHNOTE_API_KEY` | Yes | Highnote API key (test or live). |
| `HIGHNOTE_ENVIRONMENT` | Yes | `test` or `live` (default: `test`). Gates `/api/simulate/*` off in `live`. |
| `HIGHNOTE_CARD_PRODUCT_ID` | Yes | AP invoice automation card product, ODF-enabled. |
| `HIGHNOTE_APPLICATION_ID` | Yes | Subscriber or business account holder application. The backend derives the account holder ID from this at boot. |
| `WEBHOOK_PUBLIC_URL` | No | Public URL to register with Highnote. On Render, leave unset — `RENDER_EXTERNAL_URL` is auto-detected. Set this only for local-tunnel testing (ngrok, etc.). |
| `JWT_SECRET` | When `NODE_ENV=production` (any hosted instance) | JWT signing key. Auto-generated by Render; set explicitly on other hosts. In local dev a per-process random secret is used and tokens invalidate on restart. |
| `PORT` | No | Defaults to `3000`. |
| `LOG_LEVEL` | No | Defaults to `info`. |
| `CORS_ORIGIN` | No | Defaults to `http://localhost:5173` in dev and same-origin only in production. |
| `CSP_REPORT_ONLY` | No | When `true`, the CSP is delivered as `report-only` for soak-testing changes. |
| `SQLITE_PATH` | No | SQLite file path. Defaults to `./data/app.db`. Render's blueprint sets this to `/app/data/app.db`. |

The full set with comments lives in [`.env.template`](./.env.template).
